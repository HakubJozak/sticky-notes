Sticky notes → live delivery to Claude Code

How review notes pinned in the browser reach the running Claude Code session without copy and paste. Components, lifecycles, the Send flow, session selection, screenshots, what each kind of page can do, failure modes, and the reasons behind the shape. Scope of v1: Rails apps (local or remote) and local HTML files; published artifacts keep Copy Markdown.

The MCP server is the only piece Claude Code knows about. The daemon is invisible to it, which is what allows one daemon to serve every review session on the machine.

Topology and who initiates

Starting a review session

Only sessions started for review get the MCP server, so other sessions never spawn anything and never appear in the picker. Two launch flags are needed, so they live in one function:

# ~/.config/fish/functions/claude-review.fish
function claude-review
    claude --mcp-config ~/projects/sticky-notes/mcp.json \
           --dangerously-load-development-channels server:sticky-notes $argv
end

claude-review                 # new review session
claude-review --resume <id>   # the session you just left (id printed at exit), now with a channel
  • Why at launch. Claude Code registers channel listeners when it starts and says so in its banner. Nothing can arm a running session; a /sticky-notes skill can only print the command above.
  • Upgrading a running session. Leave it, then claude-review --resume <id> with the id printed at exit. Conversation and context survive, only the process restarts.
  • Daemon lifecycle. The first MCP server that finds no daemon.sock spawns the daemon detached (own session id, stdio to a log file) and then connects. The daemon keeps running after every session is gone; it is idle and small. node server/daemon.js stop ends it.
  • After the research preview. The flag becomes --channels server:sticky-notes, still per launch by design, so the function stays.
  • Cost. One idle node process per review session plus one daemon per machine, and the warning dialog once per launch during the preview.

The Send flow

Choosing the session

The daemon's session table is the set of open MCP server sockets, each tagged with the cwd, pid and label registered at connect. Only the reviewer knows which session a note is for, so the bar shows a picker whenever more than one is live.

Screenshots

A screenshot taken while a note is focused attaches to that note. On Send it travels in the same request, the daemon stores it as a file, and the event carries the path. Claude reads the file only if it decides to, as a native image.

  • Attach. "▭ Screenshot" while a note is focused attaches the blob to that note; with no focused note it stays standalone as today. The bar counts pending screenshots.
  • Auto-shot (toggle, default on). On Send, the overlay re-renders each noted element's box with padding and attaches it, so Claude sees every noted element without manual screenshots. About 100–500 ms per note.
  • Storage. Pending blobs live in memory until sent; a reload before Send loses them and the bar says so.
  • Format. JPEG for photos of UI is fine and universally readable; WebP would be smaller but adds nothing the token budget notices.

The overlay decides at mount: data-channel present → Rails path (Connect is never offered there: the daemon lives on the app's machine, not the browser's); a daemon token in localStorage → direct path; otherwise no Send button. The Markdown body is identical everywhere, so the skill's "reading the export" section holds for all of them.

Artifacts later: the database mailbox

A published artifact cannot reach the daemon, but claude.ai attaches a small JSON document store to each artifact when it is published with capabilities: {db: {}}. Page code reaches it through claude.use("db"); the Claude Code session reads the same store through the Artifact tool's read_db action, as the owner. That gives a mailbox, not a push:

  1. The overlay is injected as today and the artifact is published with the db capability declared. Without it use("db") resolves null and the overlay hides Send.
  2. Send writes one document per batch under sticky-notes/<key>/batches/<timestamp>: url, key, title, Markdown, note records, screenshots as base64 JPEG (document size limit to verify; large images may need sibling documents). The viewer consents once on the first write.
  3. Nothing wakes the session on a write. The reviewer leaves a comment on the artifact with "Send to Claude", which notifies the publishing session, or says "check notes" in the terminal.
  4. The session lists the batches with read_db (out_dir keeps payloads out of context), decodes screenshots into shots/, acts, then marks each batch delivered: true with write_db.

Deferred because reviewing artifacts is rare here, the path shares no code with the daemon design, and it costs one extra gesture per round anyway. Two other capabilities were considered and dropped: a page republishing itself (artifact) does notify the session but rewrites the whole HTML per Send and races the agent's own republishes; room reaches only viewers present right now and persists nothing.

Rails engine

  • GET /sticky-notes/sessions: reads daemon.json, calls the daemon, returns the list ordered for this Rails.root. 503 when the daemon is unreachable.
  • POST /sticky-notes/notes: forwards the body to the daemon with the token, returns its status and JSON unchanged.
  • sticky_notes_tag renders data-channel="/sticky-notes" and data-channel-token whenever the channel is on — the page, not the render path, discovers whether a daemon answers. Both routes exist only when StickyNotes::Rails.channel? (development, or config.sticky_notes.channel = true), and both need the page token.

The event Claude receives

<channel source="sticky-notes" url="https://krouzitko.oak.hozak.dev/kids/12" key="/kids/12" count="2">
# Notes on Kid 12

1. `#kid-form [name="kid[name]"]`
   > Name
   under: Details
   Label is cut off at 1280px
   screenshot: /home/dev/.cache/sticky-notes/shots/s2/kids-12-1.jpg
2. `#kid-form button[type=submit]`
   > Save
   under: Details
   Should be disabled until the form is dirty
</channel>

The body is the Markdown the overlay exports today plus a screenshot line where one was attached. The MCP server's instructions tell Claude that events are review notes for the page in url, to Read referenced screenshots before acting, and that no reply is expected.

Security

  • Daemon listens on 127.0.0.1 only; every call needs the token from daemon.json (mode 0600). Remote reach exists only through the app in front, and the proxy takes only calls carrying the page token — 32 hex of SHA256("sticky-notes:" + secret_key_base) (stable across puma workers and restarts), rendered as data-channel-token and sent as Authorization: Bearer, which also forces a CORS preflight the engine never answers, so a hostile page cannot post notes into the reviewer's session.
  • The engine exposes its two channel routes in development only, unless the host sets config.sticky_notes.channel = true (a staging box behind a VPN). The overlay itself stays on in staging.
  • File names are generated by the daemon; nothing from the page becomes a path. Images are validated by magic bytes, not by declared type.
  • Channel content is review text for the page; the MCP server's instructions frame it as data, and Claude's normal permission prompts still apply to whatever it does next.

To verify in the first spike

  1. Verified: a stdio server from --mcp-config runs in Claude Code's own cwd. Needed for picker ordering only.
  2. Verified: the environment carries CLAUDE_CODE_SESSION_ID and no name, so the picker labels a row by the cwd's basename.
  3. That servers spawn at launch, not on first tool use. Channels need the process running before the first Send.
  4. Verified: --resume <id> with the extra flags restores the conversation and spawns the MCP server. --continue picks the latest conversation in the cwd, which from ~ is usually another session.
  5. That a daemon spawned detached outlives the MCP server and Claude Code.
  6. Whether reading ~/.cache/sticky-notes/shots/… from a session started elsewhere prompts for permission.

Design notes

choicereason
channels rather than tools, resources or hooksthe only mechanism Claude Code offers for an external event to enter a live session unprompted. Tools need the model to call them, resource updates carry no payload and are ignored unprompted, hooks fire only on the session's own events
a stdio MCP server per sessionchannels must be stdio subprocesses of Claude Code; an HTTP MCP server's notifications are never delivered
a daemon behind itliveness for free (sockets), one stable address for the engine, buffering when no session is live, room for replies later. About 30 lines more than one process per session with registry files, which needed pid sweeps and had none of that
Rails proxy rather than direct loopback POSTa direct POST points at the reviewer's machine when browsing remotely and leaks the token into the page. Same-origin to the app costs nothing
not a caddy route to the daemonviable now that the port is fixed, but it means editing caddy per host; kept as the option for static pages behind caddy
launch-time only, via claude-reviewa user-scope registration would spawn the server in every session, clutter the picker and still need the per-launch channel flag
explicit "queue" entry in the pickerbuffered notes would otherwise go to whichever session registers next, which may not be the one you meant
files, not inline imagesClaude Code holds tool-result and event images as base64 text; a Read on a file is a native image and is paid only when used
JPEG at CSS scale with a 1568 px captoken cost follows pixel area; the cap is what saves tokens, JPEG is what saves disk and transfer
loopback port rather than a unix socket for RailsRuby HTTP clients want TCP; on one machine port plus token is the same security
